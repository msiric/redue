# REDUE agent instructions

REDUE preserves verification outcomes and independently decides whether they
apply now. Ship useful, truthful improvements with the existing evidence engine.

## Start and resume

Read `STATUS.md`, check the branch and working tree, then take its highest-value
unblocked task. `STATUS.md` is the only required project-memory reading;
`DECISIONS.md` is an index. Open detailed plans, reviews and history only when the
task needs them. Preserve the existing REDUE-PE-001 goal and current local work.

## Delivery

- One coordinator; delegate bounded independent work when it saves time. Keep one
  writer per interface and use approved included capacity (at most four agents).
- Deliver one coherent user outcome per PR. Run targeted checks while working and
  relevant full/platform checks at the release boundary, not after every edit.
- Independent review is required for receipt selection, applicability, trust,
  authentication and security-boundary changes. Review the complete candidate,
  including bindings and tests; ordinary changes need tests and normal CI.
- Review exact commits in an isolated checkout or Git objects. Tests may run in
  an owned verification workspace within effective host permissions. Green tests
  are evidence for the tested conditions, not universal safety certification.
- Avoid new subsystems/native helpers/workflows without a short justification.
  The sealing experiment is frozen. Do not increase its budget or resume it.
- Preserve necessary compiler/artifact/producer digests. Add no new hashes of our
  own source unless an actual execution/trust boundary requires them; remove old
  ones only with review of that boundary, not a blanket search-and-delete.
- After two materially different failures, stop the approach, state the evidence
  and alternatives (including narrowing the claim), and take another useful task.

## Product and authority

Historical PASS/FAIL stays immutable; stale or unknown evidence is never green.
Imported evidence never supplies recipient observation, caller authority or trust.
The approved next task is evaluating a narrower controlled-CI producer contract;
its exact assumptions need review before enabling a new interpretation. Existing
counterexamples and withdrawn interpretations remain preserved and refused.

Keep actual agent/machine acceptance distinct from mocks, source review and CLI
replay. Failed prerequisites launch no model. Measure complete verification paths,
including recording/reruns/setup; publish no invented savings or adoption claims.

Routine implementation, task pushes and reviewed in-scope integrations are
approved. Publication/tags, new cost, credentials, broader permissions/trust and
material guarantee changes remain owner decisions. Additional spending is $0.
Use only established included capacity. Batch genuine owner needs and continue
unblocked work; do not ask for routine hashes, filenames or test commands.

## Operations and records

Use `/bin/bash` with `login: false`; zsh startup may run an unrelated credential
updater. Preserve sandbox/proxy controls, private evidence and normal installs.
For GitHub operations use the approved personal `msiric` account. Diagnose the
actual account before calling a403 a host denial. The reviewed process-local
existing-account route is in docs/plan/director-role.md; never log/save credentials
or change the shared default. Git authentication remains separate.

Keep `STATUS.md` under150 lines and overwrite current state; history lives in Git,
PRs and protected local evidence. Update it with the work it describes. Do not
make repeated status-only commits, append duplicate checkpoint chains, or create
another tracker. Link measurements, failures and reviews rather than repeating
full reports. Retain immutable receipts and the frozen alpha.11 artifact.
